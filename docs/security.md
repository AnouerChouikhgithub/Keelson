# Security notes

This file describes what the code enforces today and how it was verified. It is
not a threat model for a specific deployment: TLS, network policy and host
hardening are the operator's responsibility (see
[deployment.md](deployment.md)).

## Identity and sessions

- Passwords are hashed with Symfony's `auto` hasher (argon2id/bcrypt depending on
  the platform); the plaintext is never stored, logged or echoed.
- Authentication is a server-side session in PostgreSQL (`sessions` table) with
  `HttpOnly`, `SameSite=Lax` and `Secure` whenever the request is HTTPS
  (`cookie_secure: auto`). The session id is regenerated by Symfony on login, and
  `POST /api/auth/logout` invalidates the session server-side.
- A password change or reset invalidates other sessions through Symfony's stored
  hash comparison, so a stolen session does not survive the reset.
- Sign-in is rate limited per address (5/minute) and per client address, and the
  throttle answers `429 too_many_login_attempts`. Registration, resend and
  subdomain availability have their own limiters
  (`config/packages/rate_limiter.yaml`).
- Registration, forgot-password and resend-verification are enumeration-safe:
  unknown and known addresses receive the same status and body, and no mail is
  sent for an unknown address.

## Single-use tokens

Email verification and password reset use 32 random bytes, base64url-encoded.
Only `sha256(token)` is stored; the plaintext exists in the mail and in the
redeeming request.

Redemption is **one conditional statement**:

```sql
UPDATE auth_tokens SET used_at = :now
WHERE token_hash = :hash AND type = :type
  AND used_at IS NULL AND expires_at > :now
RETURNING principal_id
```

`App\Repository\AuthTokenRepository::consume()` runs it, and
`App\Service\AuthTokenService::redeem()` wraps it and the account mutation in one
transaction. Consequences, each covered by
`tests/Integration/AuthTokenRedemptionConcurrencyTest.php`:

- two concurrent redemptions of the same link cannot both succeed — PostgreSQL
  serialises them on the row and the loser updates zero rows;
- an expired token matches no row;
- a used token cannot be replayed;
- a mutation that throws rolls the consumption back, so the link still works
  after a failed attempt;
- unknown, expired and used tokens all answer the identical
  `400 invalid_token`.

Issuing a new link marks the previous unused one used, so an older email cannot
be redeemed after the user asked for a new one.

## Tenant isolation and authorization

- Every tenant route resolves the organization through the caller's **active
  membership**; voters (`InvoiceVoter`, `OrganizationVoter`, `PrincipalVoter`)
  re-check it on every request.
- Repositories that read tenant rows join the membership in the query, so a
  foreign identifier returns no rows rather than someone else's row.
- A denial is `404`, identical to a missing record, so the API does not confirm
  that a foreign record exists.
- `tests/Integration/RouteIdorTest.php` walks every route with an identifier as a
  foreign tenant and anonymously; `InvoiceAuthorizationMatrixTest` covers the
  role matrix (Owner/Admin/Member/Viewer, suspended membership).
- PostgreSQL row-level security is enabled and **forced** on `customers`,
  `invoices`, `invitations` and `notifications` (ADR 0003). Each policy admits a row
  only when `organization_id = current_setting('app.organization_id', true)::uuid`,
  and the same predicate guards writes, so a foreign `INSERT` is refused by the
  database. `App\Tenancy\TenantContext` sets the value transaction-locally, which
  means it is discarded on commit and cannot leak on a reused connection. A missing
  setting yields **no rows**, never all of them.
- Notifications are the one cross-tenant read: the policy also accepts rows whose
  `principal_id` matches `app.principal_id`, because the inbox spans every
  organization the person belongs to. Its write check stays tenant-only.
- `principals`, `memberships`, `auth_tokens` and `sessions` are deliberately outside
  the policies: they are read before a tenant is known. Their authorization remains
  the voters and the repositories above.

## Last-owner invariant under concurrency

`PATCH/DELETE /api/organizations/{id}/members/{membershipId}` take a
transaction-scoped advisory lock per organization
(`MembershipRepository::acquireOwnerGuard()`), **then** re-read the requester and
the target and only then count the remaining active Owners. Two Owners demoting
or removing each other at the same time therefore serialize: the second request
sees the first one's committed result and answers `409 last_owner`.

The count excludes suspended memberships and only counts `active` rows on an
`active` organization. `tests/Integration/LastOwnerProtectionTest.php` covers
demotion, removal, self-removal, the Admin/Owner boundary, the lock itself (a
second connection holding it makes the request wait) and a change committed
before the request.

## Browser-side session handling

- The CSRF token lives in memory only; it is never written to `localStorage`,
  `sessionStorage` or a cookie of the application's own.
- Tabs stay in step through `BroadcastChannel`, with a `storage`-event fallback
  (`frontend/src/session/sync.ts`). A message is only a hint: each tab re-reads
  `GET /api/session`, and a changed principal drops all cached tenant reads.
- A tab revalidates the session when it becomes active again (at most once per
  30 seconds, so alt-tabbing does not poll), and a `401` from any request tells
  the provider to re-read the session instead of inventing a signed-out state.
- Requests are same-origin only (ADR 0006); no credentialed CORS is enabled.

## CSRF and request shape

- Every unsafe `/api` request must come from the same origin when it sends an
  `Origin` header, and an authenticated one must also carry `X-CSRF-Token`
  matching the session's `api` token. The only exemptions are the token/credential
  endpoints reachable before a session exists; logout is deliberately **not**
  exempt.
- Unsafe requests must declare `Content-Type: application/json` when they declare
  a type at all; a form or text type is `415`.
- Bodies over 1 MiB are `413`; JSON nested deeper than 16 levels is `400`.
- Validation errors use the shared `{error:{code,message,fields}}` envelope, and
  internal exception messages never reach a client
  (`App\EventListener\ApiExceptionListener`).

## Headers, logging and the audit trail

- `/api` responses send `nosniff`, `strict-origin-when-cross-origin`,
  `camera=(), microphone=(), geolocation=()`, `default-src 'none'; frame-ancestors
  'none'`, `no-store, private` when authenticated, and HSTS only in production
  over HTTPS. The SPA document policy is set by `frontend/nginx.conf`.
- Structured JSON logs redact tokens and password material; a request id
  correlates entries.
- `security_events` records `login_success`, `login_failure`,
  `password_changed` and `invitation_accepted` with IP, truncated user agent,
  request id and a small data map. A failed sign-in stores a 16-hex fingerprint of
  the address, never the address; a test scans the table for passwords and tokens.
- Invoice audit events are append-only at the database level (a trigger refuses
  update/delete) and are written in the same transaction as the operation.

## Dependency audit (2026-11-17)

| Ecosystem | Command | Result |
| --- | --- | --- |
| PHP | `composer audit --locked` | No security vulnerability advisories found. |
| JavaScript (frontend) | `pnpm audit --audit-level high` | 1 moderate: `minimatch` ReDoS (GHSA-g3hv-75wg-m249), patched in `>=11.0.1`. 1 high, accepted: `picomatch` ReDoS (GHSA-fc5q-39xc-vjpf), **no patched version published**; already at the latest release (4.0.7). |
| JavaScript (e2e) | `pnpm audit --audit-level high` | No advisories above moderate. |

Both packages are transitive dev dependencies of the build and test tooling
(ESLint, Vite/Vitest, knip, Playwright) and never ship to a browser.

- `minimatch` is pinned below its patched release by the installed ESLint line;
lifting it needs a major ESLint upgrade (and a matching `typescript-eslint`) — a
dependency decision for the owner, not a silent bump. It is **moderate**, so the
`--audit-level high` gate does not fail on it.
- `picomatch` 4.0.7 is the newest published version and the advisory lists no
patched release, so there is nothing to upgrade to. Rather than turn the audit
job permanently red (which would train everyone to ignore it), the specific GHSA
is listed in `frontend/pnpm-workspace.yaml` under `auditConfig.ignoreGhsas`,
which is what `pnpm audit` reads. That is a scoped, visible acceptance: `pnpm
audit` still prints `1 ignored: 1 high`, and every other advisory still fails the
job. Re-check it when `picomatch` publishes a fix, then remove the entry (or run
`pnpm audit --fix`).

CI runs `composer audit --locked` (no install needed) and both pnpm audits in one
job; the job fails if **any** of the three reports a problem, and the JavaScript
audits still run when the PHP one fails.

## Not implemented

- Row-level security on the identity tables (`principals`, `memberships`,
  `auth_tokens`, `sessions`); see ADR 0003 for why they stay application-layer.
- A suite-wide run as the application role: the database suite still connects as the
  schema owner, and the policies are asserted by `RowLevelSecurityTest` on a
  dedicated non-`BYPASSRLS` role.
- Multi-factor authentication, social login, enterprise SSO.
- Email change (an address is fixed at registration).
- A "signed-in devices" screen or "sign out everywhere" button.
- Content-Security-Policy nonces for the SPA (inline `style` attributes require
  `style-src 'unsafe-inline'`; there is no third-party script).
- Secret rotation tooling; `APP_SECRET` rotation signs every session out, which is
  documented but manual.

## How this was verified

- `php bin/phpunit` against a disposable PostgreSQL 16 (counts:
  `bash bin/test-counts.sh`), including the token, last-owner, IDOR, CSRF, auth,
  invoice and audit suites.
- `composer stan` (PHPStan level 8 plus the dead-code detector, no baseline) and
  `composer cs`.
- The Playwright journeys in `e2e/` over the real stack (sign-up, invoice
  lifecycle, invitation, viewer read-only, throttling, locales).
- A manual HTTP pass with `curl` for status codes and headers, and a Docker
  Compose production run.
- **Not** verified in this environment: TLS termination, a real SMTP provider,
  and any external identity provider (there is none).
